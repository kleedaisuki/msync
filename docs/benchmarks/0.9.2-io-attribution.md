# msync 0.9.2 I/O bottleneck attribution

2026-11-20 · Linux x64 Native AOT · ext4 on a KVM guest · warm-cache
same-host OpenSSH 10.0p2 · client and receiver pinned to logical CPU 6.

The [distribution baseline](0.9.2-linux-x64.md) showed that a 377-file, 5.53 MiB
tree took longer to copy locally and upload than a 103-file, 45.75 MiB
artifact batch. The two reversals have different causes: serial file sync
locally, and the per-entry remote shell installer on upload. Download stages
files locally and pays the file sync cost alongside stream consumption.

## Evidence and priority

**Local: file sync, not file enumeration or byte copying, dominates the
small-file tree.** Diagnostic transfer time is 471/440 ms; inclusive
`file.copy` is 458/431 ms, of which `file.sync` accounts for 376/344 ms
(about 80% of the transfer). `file.publish` accounts for 22/32 ms.
A separate telemetry-off `strace` run verifies 377/378 successful staging
file `fsync` calls and the same number of renames. The code walks the tree
serially and finishes the [staging file flush and rename](../../src/Msync.Runtime/Transfers/TransferFiles.cs)
before the next file. Compile and preparation medians across all cells were
under 9 ms and 16 ms respectively.

**SSH upload: remote publication dominates the source tree.** The transfer
median with diagnostics is 1,738/1,718 ms; the inclusive client-side archive
span is 303/282 ms. About 1,431 ms elapses from the end of that span to the
end of transfer, whereas the eventual `transport.exit_wait` is below 1 ms
at the median. The gap includes archive finalization and
[waiting for the remote receipt](../../src/Msync.Runtime/NativeModel/NativeHostIO.Remote.cs);
it is not itself an isolated server duration.

The receiver [extracts once, then installs recursively](../../src/Msync.Runtime/NativeModel/NativeHostIO.Protocol.cs).
A separate receiver-side `strace -f` on the foreground shell, with telemetry
off, observes 377/378 `mv`, 427/428 `mkdir`, and 48 each of `stat`,
`chmod`, and `touch` on the source tree: roughly 950 external commands.
The artifact batch uses 103/104 `mv`, 122/123 `mkdir`, and 17 each of the
three directory metadata commands. These are command counts, not fork
counts or a timing speedup estimate.

In another three checked rounds per shape and phase, a fixture-only remote
`PATH` shim logged `tar` before/after and the final stage-cleanup `rm`
before/after. msync telemetry was off; there was no `strace`. Elapsed time
from `tar` return to cleanup launch (essentially publication) was **1,506/1,458
ms** for the source tree and **413/457 ms** for the artifact batch. The
extract-and-receive interval was 231/101 ms and 451/458 ms, respectively.
The wrappers add a small fixed cost per invocation and these are separate
observations, not spans subtracted from the primary CLI timings.

**SSH download: the small-file sync cost is still on the serial path.**
Archive installation awaits each local staged write before consuming the
next entry. For the source tree, `file.sync` consumes 403/407 ms of
1,050/1,060 ms diagnostic transfer time (about 38%); inclusive `file.write`
is 813/801 ms. For the artifact batch, only 139/168 ms of 1,165/1,127 ms is
sync: the stream and local write path matter more for this shape.

**Priority.** Start with the upload installer: avoid re-creating the known
parent for each leaf, prototype same-filesystem subtree rename for absent
targets, and reduce helper launches on populated merges. Check metadata,
symlink/overlap behavior and receiver-owned names before replacing the
current path. The [GNU mv contract](https://www.gnu.org/software/coreutils/manual/html_node/mv-invocation.html)
also permits a cross-filesystem copy fallback; that is not an atomic
rename fast path. Separately prototype bounded staging/flush overlap for
local copy and download, keeping one flush per staged file, atomic
publication, and existing cancellation/failure behavior. The
[ext4 batching documentation](https://docs.kernel.org/admin-guide/ext4.html)
makes concurrent sync a reasonable probe, not a guarantee of improvement.
Add receipt-wait and receiver extraction/publication observations when
changing the upload path. Measure on a normal CPU allocation and real
storage before making production speedup or WAN claims.

The separation by namespace and byte distribution follows the [FAST '07
filesystem metadata study](https://www.usenix.org/conference/fast-07/five-year-study-file-system-metadata);
it does not assume those file populations describe msync usage.

## Implementation and acceptance

The upload receiver can publish an absent root with a single no-clobber,
rename-only move. That path applies only to an upload's fresh staged root,
not to a relay, a peer-side copy, or a descendant of an existing merge
target. Those paths can have different directory-ownership inheritance.
An older GNU `mv` without `--no-copy`, or an attempted move that leaves the
source staged, uses the same recursive merge. GNU added the optional
[`--no-copy` capability in coreutils 9.2](https://lists.gnu.org/archive/html/info-gnu/2023-03/msg00005.html);
it is not a receiver prerequisite. Recursive installation avoids repeating
`mkdir` for each leaf, avoids a shell subshell per member, and preserves
directory mode/mtime restoration after child publication.

Linux local directory copies and directory downloads can have four small
regular files (up to 64 KiB each) in flight per transfer. The producer reads
and stages bytes in order and retains one stream cursor; only the private
file flushes overlap. The consumer publishes in order after each file's
single successful flush. Directory and link effects drain pending work;
large files keep the direct path. An error retires later private stages,
not already published members. This retains the distinction between
per-file atomicity and whole-tree persistence discussed in the [OSDI
filesystem persistence study](https://www.usenix.org/conference/osdi14/technical-sessions/presentation/pillai).

Focused Native AOT journeys covered the actual OpenSSH rename, a simulated
older `mv` capability and a raced no-clobber skip, existing-tree merge,
same-endpoint copy and cross-endpoint relay, source/object/bound ELF routes,
nanosecond file/directory/link metadata, failed rename with a stable published
prefix, truncated download without replacement of the old file, and
retained-input cancellation. Two pre-existing auxiliary scripts
(`shell_source_newlines.py` and `ssh_diagnostics.py`) also fail on the release
control; their failures were not used as acceptance for this change.

### Paired Linux Native AOT results

The frozen release executable above was compared against SDK 10.0.403 Native
AOT candidate SHA-256
`a52e7976ab547ffe94808c7889b549d17fca772a4275ab31d22a165fe61f0fa9`.
Seven alternating pairs, one warmup per image and workload, CPU 6, the same
three distributions at seed 17, and telemetry off. All 252 timed deployments
met the independent content/metadata oracle. Percentages are medians of
per-pair relative changes, not ratios of the two absolute medians.

```sh
taskset -c 6 python3 tests/Performance/sync_journey.py --binary CANDIDATE \
  --baseline RELEASE --seed 17 --samples 7 --warmups 1 \
  --profile source-tree --profile release-v1 --profile artifact-batch \
  --transport local --transport ssh-loopback --transport ssh-download
```

| Transport | Profile | First deploy, baseline → candidate (ms; paired change) | Redeploy, baseline → candidate (ms; paired change) |
| --- | --- | ---: | ---: |
| Local | Source tree | 474 → 356; −21.2% | 486 → 364; −22.2% |
| Local | Mixed release | 147 → 143; −3.5% | 145 → 145; −0.1% |
| Local | Artifact batch | 234 → 218; −12.7% | 247 → 224; −8.5% |
| SSH upload | Source tree | 1,722 → 267; −84.2% | 1,716 → 1,107; −36.7% |
| SSH upload | Mixed release | 605 → 239; −61.7% | 641 → 449; −29.3% |
| SSH upload | Artifact batch | 1,053 → 622; −39.2% | 1,099 → 889; −20.7% |
| SSH download | Source tree | 965 → 842; −16.7% | 990 → 843; −11.2% |
| SSH download | Mixed release | 565 → 567; −6.7% | 550 → 537; −5.2% |
| SSH download | Artifact batch | 1,141 → 1,019; −3.1% | 1,011 → 1,074; +6.3% |

Separate source-tree diagnostics observed one root rename on first upload
and 378 leaf moves plus 48 recursive directories on redeploy. Client receipt
wait was 10/808 ms. The local and SSH download traces still recorded 377/378
file flushes, respectively; the new queue reached depth four and the sum
of sync spans could exceed the union. The speedup does not come from
removing durability calls. Diagnostic durations are illustrative single
recordings, not part of the paired samples.

The source-tree check with CPU affinity 0–11 (five alternating pairs per
cell) also favored the candidate in every pair: paired reductions were
48%/50% locally, 82%/38% for upload, and 31%/36% for download. Affinity and
loopback effects mean the absolute latencies are not cross-machine results.
In a nine-pair artifact-only download recheck the +6.3% redeploy loss did
not reproduce: paired medians were −8.1% first deploy and −3.2% redeploy.

The compatibility follow-up keeps implicit parent-directory creation for
archive paths that do not include a directory header. It only affects
queued download staging. Final executable SHA-256:
`fd0d2522eb9957a387709c4b5d7059118e8eb548c219afbfb7028f3591b068fa`.
The truncated archive journey includes a complete file under an implicit
parent: that file must be published before the invalid member fails, with
the previous target and all unrelated state intact.

The final SSH download group repeated all three profiles at CPU 6, seven
alternating pairs per cell, with 84 checked observations:

| Profile | First deploy, baseline → final (ms; paired change) | Redeploy, baseline → final (ms; paired change) |
| --- | ---: | ---: |
| Source tree | 973 → 787; −21.8% | 946 → 817; −19.0% |
| Mixed release | 556 → 532; −4.4% | 539 → 549; −0.9% |
| Artifact batch | 1,054 → 1,021; +1.4% | 1,123 → 1,013; −4.2% |

Treat bulk download as inconclusive for a general speedup: first-deploy
paired changes varied by run window and the absolute medians can differ
in direction from the paired relative estimator. Neither the isolated
recheck nor the final group repeated the initial redeploy loss. The
small-file download benefit repeated across both builds and CPU affinities.
