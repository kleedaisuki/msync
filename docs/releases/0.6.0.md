# msync 0.6.0

Version 0.6 adds typed control flow and lazy filesystem selection to the existing
compiled synchronization language. The subsequent locally accepted
optimization/tooling work stays at 0.6.0 and preserves those language semantics.
A version number or this document does not establish that release assets were
published; measured acceptance and artifact identities are recorded separately.

## Language additions

| Addition | Contract |
| --- | --- |
| `delete path` / `delete "filename"` | Remove a file at execution; not recursive directory deletion |
| `name = true` / `name = "text"` | Declare or update same-typed boolean or string data |
| `boolean name(args): ... return expression` | Pure boolean function; return is mandatory and must have boolean type |
| `exists path` / `exists "filename"` | Runtime path-existence query returning a boolean |
| `range \| views::filter(predicate)` | Typed lazy view pipeline over paths or strings |
| String `> < >= <= == !=` | Case-sensitive lexicographic comparisons returning boolean |
| `if` / `else if` / `else` | Indentation-sensitive selection with boolean-only conditions |
| `for item in range:` | Demand-driven range iteration |
| `loop:` / `break value` | Nearest-loop exit; loop expressions yield string, path, boolean or space |
| Nested definitions and `global` | Independent lexical invocations with explicit definition-time ancestor imports |
| `drop a, b` | Remove lexical bindings/templates, not filesystem resources |

Booleans support `true`, `false`, `and`, `or`, `not`, parentheses, `==` and `!=`.
There is no string/path truthiness conversion. Pure computations fold or inline
when possible; filesystem state never becomes a compile-time constant. Both
operands are statically checked even when execution can short-circuit.
`=` can update an existing boolean or string without changing its type. Writes
inside `if`, `for` and `loop` are visible afterward in the same invocation;
fresh names declared in a branch or loop do not leak into its parent scope.

```text
boolean any(a, b, c):
    return a or b or c

name = "klee"
"payload" -> scratch.txt
was_present = exists scratch.txt
delete "scratch.txt"
if any(false, was_present, name < "q"):
    name -> result.txt
else:
    "not selected" -> result.txt
```

An existence binding records one execution-time observation. In this example,
`was_present` remains true after deletion; using the binding does not perform a
new query. A later `exists scratch.txt` makes a fresh observation.

`exists` follows symbolic-link targets: a dangling link is false and a directory
is true; permissions and symlink-loop failures are reported rather than hidden as
false. `delete` unlinks a symbolic link without deleting its target, and rejects
actual directories and special files. Local/environment paths and existing WSL
and SSH adapters support these operations. PATH supports existence lookup but is
read-only; HTTP and TCP do not support filesystem queries/deletion. Regex ranges
enumerate directory-capable local/environment, WSL or SSH endpoints, not PATH.
Remote filesystem helpers retain the existing GNU-tooling prerequisite.

## Ranges and loop results

Regex selection now produces a lazy range. A range expression is a plan, not an
instruction to enumerate during compilation or declaration. `filter` requires a
boolean predicate; `transform` requires a path/string projection. Boolean queries
consume a range and produce a scalar boolean, never a range of booleans.

```text
boolean present(path):
    return exists path

symbol identity(path):
    return path

files := inputs/<.+\.txt>
for file in files | views::filter(present) | views::transform(identity) | views::take(1):
    file -> first.txt
if files | ranges::any_of(present):
    "matched" -> status.txt

message = loop:
    loop:
        break
    break "complete"
message -> completion.txt
```

The [range contract](../design/ranges-v6.md) records supported adaptors, scalar
consumers, aliases and domain limits:

| Family | Operations |
| --- | --- |
| Sources | Regex selection, `ranges::of(...)`, `views::single(value)` |
| Lazy views | `filter`, `transform`, `take`, `drop`, `take_while`, `drop_while`, `stride`, `unique`, `reverse` |
| Identity views | `all`, `common`, `as_const`, `as_rvalue` |
| Boolean consumers | `empty`, `contains`, `any_of`, `all_of`, `none_of` |
| Element consumers | `front`, `back`, `find`, `find_if` |

Both `items | views::filter(predicate)` and `views::filter(items, predicate)`
are accepted. Counts are compile-time decimal constants; `stride` must be
positive. `unique` removes adjacent duplicates, not all duplicates globally.
`front`/`back` on an empty range and `find`/`find_if` without a match report
runtime errors; they do not return a fabricated empty path or optional value.
Numeric sequences, tuple-valued views and
nested ranges are not implied by the C++-style interface: range elements are
strictly paths or strings. Ordering is deterministic entry-name ordering; this
can buffer names without eagerly executing predicates or opening selected files.
A zero-sized `take` must not pull its input. Consumers short-circuit where their
result permits it.

All breaks associated with a value-producing loop must agree on type. Nested
breaks target their nearest loop. An ordinary `break` without a value exits a
statement loop. `for` accepts ranges, not scalar paths or strings.
Open-ended loops check cancellation every iteration and yield to the runtime;
they have no arbitrary fixed iteration cap.

```text
done = false
message = "working"
loop:
    if done:
        break
    message = "complete"
    done = true
message -> result.txt
```

The second iteration observes the updated `done` and exits; `result.txt`
contains `complete`. This is assignment to existing invocation state, not a new
shadow binding created on each iteration.

## Lexical scope and removal

A macro may locally declare macros, symbols and booleans; a symbol may locally
declare symbols; a boolean may locally declare booleans. Definitions are
invocation-local and do not escape. `global` imports a previously declared name
from the definition's lexical ancestry, including ancestor macros, not the
unrelated caller's local bindings.
Parameters and imported globals are invocation-local values: assignment inside
a macro, symbol or boolean does not provide a reference for mutating its caller.

```text
Codex := ~/.codex
macro codex():
    global Codex
    macro copy():
        global Codex
        acquire Codex/config.toml -> s.txt
    copy()
codex()
drop Codex, codex
```

`drop` removes bindings and callable definitions; it does not delete `s.txt`,
release live program ownership, or promise immediate resource reclamation.
A reference already captured by an earlier definition retains its lexical value.

## Compiler and object compatibility

`# msync: 0.6` and `--syntax 0.6` select the default grammar. Existing 0.5 headers
and flags remain accepted compatibility aliases. Removed 0.3/transactional 0.4
source syntax remains rejected; existing historical artifact support is unchanged.
The meanings of literal transfer payloads, explicit path composition and
release/acquire scheduling are retained.

Dynamic expressions and nested control regions are statically typed before any
runtime effects. The interpreter observes filesystem state at their execution
boundary, after preceding managed work. Ordinary static transfers retain the
existing fast path and publication owner. Object execution never reparses debug
source or reopens original scripts. New control semantics use an explicit feature
flag; unsupported readers must reject them rather than reinterpret an older
instruction. Context relocation must include nested control operands and range
callbacks, not only top-level transfers.

## Configuration and local observability

Application policy can be configured in TOML. Unix discovery uses
`$XDG_CONFIG_HOME/msync/config.toml`, or `$HOME/.config/msync/config.toml` if XDG
is unset/empty; Windows uses `%APPDATA%/msync/config.toml`. When the canonical
file is absent, `~/.msync/config.toml` is the fallback. These files are alternatives,
not merged layers, and cwd-local files are never automatically loaded.

```sh
msync config
msync config --config /path/to/msync.toml
msync run script.msync --config /path/to/msync.toml --jobs 8
msync run script.msync --no-config
```

Inspection prints reusable effective TOML and per-value provenance without
creating state/telemetry outputs. Precedence is defaults, selected config,
existing compatibility environment, then explicit CLI flags. Config-relative
paths follow the config directory. Unknown/invalid settings report their source
and fail before effects. `--help`/`--version` bypass config and telemetry startup.
See the [configuration reference](../design/configuration-v6.md).

SQLite recording is opt-in; JSONL remains supported:

```sh
mkdir -p .temp
msync run script.msync --telemetry-db .temp/run.sqlite
msync telemetry sessions .temp/run.sqlite --limit 10
msync telemetry summary .temp/run.sqlite
msync telemetry spans .temp/run.sqlite --limit 20
msync telemetry events .temp/run.sqlite --limit 20
msync telemetry export .temp/run.sqlite > .temp/run.jsonl
```

The database retains causal span/event identities, phase metrics, attributes and
native error causes across the end-to-end path, not only total process duration.
Queries/export are read-only; `--trace-id ID` narrows summary/spans/events/export,
and events also accepts `--span-id ID`. Explicit `--trace` selects JSONL instead
of SQLite; exporter flags conflict rather than silently choosing one.
`--no-telemetry` disables configured recording. Custom output parents must exist.
Bounded batching/backpressure and visible exporter errors preserve diagnostics;
SQLite WAL is local-host storage, not a network logging service. See
[telemetry](../design/telemetry.md) and [SQLite storage](../design/telemetry-sqlite.md).

## Native editor and language-server tooling

The versioned editor release asset `msync-language-0.6.0.vsix` contains native
TextMate coloring, language configuration/snippets and a stdio LSP client for
VS Code 1.91 or newer. Download it and `SHA256SUMS` from the same release, verify
the VSIX's listed checksum, then use **Extensions: Install from VSIX**, or:

```sh
code --install-extension msync-language-0.6.0.vsix
```

Put `msync` on PATH or set user/machine `msync.serverPath` to its trusted absolute
executable path. Opening a `.msync` document launches `msync --language-server`.
Other LSP editors can use that same command over stdio. Native coloring remains
available when server startup fails. The server provides compiler diagnostics,
completion, hover, definitions, document symbols, formatting and semantic tokens;
it never executes synchronization effects. Source expansion can read referenced
scripts, but navigation/completion remain document-local rather than a workspace
include index. See the [extension README](../../editors/vscode/README.md) for
build/audit details and the [toolchain contract](../design/toolchain-v6.md) for
capability boundaries. An automated actual VS Code 1.144.0/Electron host gate
also passed activation, diagnostic repair, formatting, completion and Unicode
semantic-token checks without DSL file effects. The identified packaged bundle
matches that real-host-tested entrypoint. This is not human visual inspection,
remote CI acceptance or a claim about unexecuted platforms; exact identities and
results are in the [editor record](../design/editor-tooling-v6.md).

Release packaging requires the VSIX alongside the platform packages before
publication. Editor and Cargo versions must agree; the release editor job runs
the actual host test against the already verified Linux portable archive rather
than compiling a second server. The release's `SHA256SUMS` is authoritative for
the published VSIX; the local acceptance record identifies its earlier tested
snapshot separately.

## Optimization and interactive behavior

This workstream compares against the frozen 0.6 baseline, not a different DSL
version. It targets repeated compiler work and lexical snapshots, graph conflict
search, preparation history scans and owned object-analysis traversals while
preserving the existing output/ordering/diagnostic contracts. The REPL waits for
runtime activity rather than periodically polling for background completion;
idle input no longer needs to receive another line to reconcile a completed job.

Mechanisms and reproducible workloads are recorded in the
[compiler](../design/performance-v6-compiler.md),
[graph](../design/performance-v6-graph.md),
[preparation](../design/performance-v6-preparation.md),
[object](../design/performance-v6-object.md),
[I/O](../design/io-linux-v3.md), and [latency](../design/latency-v6.md) notes.
These improvements do not imply one universal speedup or relaxation of endpoint,
publication, cancellation or object-compatibility constraints. The
[cross-domain acceptance record](../design/performance-acceptance-v6.md) is
separate from the earlier language gate. The
[completed requirement map](../design/optimization-roadmap.md#current-v06-completion-map-functional-and-measured-acceptance-closed)
and [final latency record](../design/latency-v6.md) name exact measured artifacts
and workloads, including the final CLI image SHA-256
`bd836d6750c855f5f4982b355ab37855f32efff4e971c6b50fe3b83f617d50c3`.

Accepted trade-offs remain explicit: tiny startup commands cost approximately
0.09–0.41ms more at p50; only about 0.11ms was directly attributed to configuration
discovery on a separate profile. The complete 100-statement independent plan
improved 1541.247→423.755ms, but that does not cancel the fixed small-command cost.
The first persistent-copy sample's negative point triggered a 202-pair
crossed-workspace discriminator, whose opposing half means and overall +0.051ms
paired mean do not establish a stable 1ms penalty or a universal zero-cost bound.
SQLite is opt-in and materially slower than disabled tracing in the measured
check/diagnostic/copy cohorts; complete recording is not advertised as free.
Mixed 1MiB TCP results are not presented as generic large-file acceleration.

## Acceptance and operational boundaries

The [integration contract](../design/integration-v0.6.md) connects frontend,
compiler, object and runtime invariants. New acceptance journeys exercise the
public CLI and real filesystem, including `check`/dry-run effect freedom,
creation/query/deletion ordering, source-free object/IR execution, nested scopes,
loop results and lazy short-circuiting. The later configuration/SQLite/editor
and event-driven runtime work has its own passing functional and measured
acceptance records linked above rather than borrowing historical test success.

Per-user installation, PATH ownership, Windows signing status and optional
transport prerequisites are unchanged. This document does not certify
Windows, WSL, remote endpoint execution or packaging acceptance. Obtain published
assets only from their matching official GitHub Release and verify SHA256SUMS.
